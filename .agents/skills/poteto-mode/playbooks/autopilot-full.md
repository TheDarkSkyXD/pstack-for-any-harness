### Autopilot-full

**You own the verdicts, never the PRs. One owner runs each PR from build to merge, and nothing merges without your clean swarm verdict.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Orchestrate runs a standing program whose coordinator lands verified work itself and whose workers never merge. Here each PR's owner carries the whole lifecycle through the merge, and the root keeps only verification, countersigns, and audits.

1. **Mark the operator's items and honor state-then-wait.** Items the operator names stay with the operator. The operator reviews and clicks, and no owner merges one. When the operator asks for the protocol or the plan to be stated, deliver the statement and stop. Execution starts only on the operator's explicit go. On that go, arm the active harness's persistent goal mechanism with the full program objective. Keep the goal active across turns until the queue is done.
2. **Spawn one owner per PR with the full lifecycle and an early trail.** One remote or isolated agent per PR owns build, registration in the repository's stacking workflow, self-proof on the real artifact (the **prove-it-works** principle skill), skeptical automated-review triage per `../references/bugbot-triage.md`, the available code-cleanup pass, `.agents/skills/no-comments/SKILL.md`, a restack onto current trunk, the babysit loop to green (`playbooks/babysit.md`), and the merge itself. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill, pushes its first branch snapshot, and opens the PR ready, never draft. Open the PR before self-proof so the URL, decisions, and checks form a durable trail. Keep `decisions.tsv` uncommitted and return it with the reports. As soon as a subagent starts, the owner adds its ID, expected runtime (at least the longest past run of that kind), and state to a `children.tsv` kept the same way. The owner does the first rebase before the code-ready report and babysit, whether or not trunk has drifted. In fix rounds, the owner keeps that merge base. The owner rebases again only at merge prep (step 5), on a `git merge-tree` conflict with trunk, or on a CI failure that comes from a change on trunk. When the shipped code is final, after cleanup and `.agents/skills/no-comments/SKILL.md`, it reports the code-ready head SHA. It also reports the SHA of each later push that changes the patch. Self-proof, CI, and babysit then run in parallel with the swarm. The owner reports merge-ready with the head SHA when self-proof, CI, and babysit finish. Before a push that starts a round, run the pre-review checks named by the repo's `AGENTS.md` files and rules for the touched paths. Run them on the committed head. A hook pass is not proof. The merge is the one step an owner may not take alone. Step 4 gates it.
3. **Run owners in true parallel and never stack.** Many owners at once when PRs are self-contained: one writer per branch, disjoint files, cross-PR drift absorbed by rebase. Only genuinely overlapping work serializes. Self-contained PRs branch straight off main, and sequenced work is merge-then-branch. Every PR is still gt-registered; the Graphite-metadata rule is about the UI, not stacks. One exception: an owner that must split a genuinely dependent change may hold a short private stack.
4. **Swarm-verify every round before its merge.** A round starts at the owner's code-ready head SHA and at each later push that changes the PR's patch. At that SHA, fan out parallel independent verifiers per the **swarm** skill and aggregate to one verdict. The merge needs a clean verdict from the round whose patch matches the merge-ready head. Audit the receipts in the merge-ready report before the verdict. Re-run gates at that SHA, prove the load-bearing behavior live on the real surface using the active harness's matching control capability, and audit the diff in two or more review lanes with separate focus. Run the same load-bearing scenario on current trunk as a regression lane. If trunk lacks the feature, record that and gate the added behavior plus the end state the user waits for. When the lanes return, send every proven finding against the PR to the owner in one fix-forward. A defect filed as a note is still a finding. For each behavior finding, ask for a red test covering every site with the same defect, or a repro receipt where no test can show it. Add it to the next round's review brief. A new head gets a fresh swarm and verdict, except results still valid under the patch-id rule in `playbooks/shipping.md`. No merge without the root's clean verdict.
5. **On a clean verdict the owner merges and takes the next item.** Merge prep never comes before a round's lanes start, and ends with a rebase onto current trunk immediately before merge. The owner reports the new head SHA, CI must pass there, and the patch-id rule decides whether the round's verdict still holds. A new head voids the verdict unless the patch-id is unchanged. The owner squash-merges its own PR and picks up its next self-contained item from the queue. The operator's full-autonomy grant plus the root's clean verdict is the merge authorization that babysitting alone never has. Operator-named items stop at merge-ready and wait for the operator's click.
6. **Run the root layer.** A genuinely new raise of a pinned gate or budget value needs your fresh countersign, granted only after verifier proof. If the operator's grant or standing orders cover approval, record it under the tool's approval contract with a pointer to the root's countersign; a lane checks the record. Never bypass forge-enforced approval. Absorbing values already on main is drift, not a raise. Run an audit tick over all owners roughly every 30 minutes using the active harness's recurring terminal, monitoring, or scheduled-wake mechanism. At each tick, re-read this playbook from trunk and the active goal, audit against both, and fix drift. Probe each owner and collect decision trails. Count only side effects as progress. A lane that errors or passes its expected runtime without a side effect is stuck; stop it and dispatch a replacement. Check the platform agent list and every owner's `children.tsv`; record and replace stuck child work too. A stall never proves or drops the work. When merges batch, run a retro pass and a post-merge bot-comment sweep. Post a concise status update only for a tracked change no earlier update reported: a PR opened, code-ready head, verification round started or closed, verdict, merge, stuck owner and response, blocker opened or cleared, or a decision the operator must make. Name each new change and nothing else. Do not repeat a queue table or unchanged blockers. If nothing new happened, end the turn without reply text. Log each audit tick in the root's decision trail, listing the changes reported or `none`.
7. **Stand down instantly on the operator's stop.** The operator's hold or stand-down reaches every owner as a zero-writes order immediately. Owners hold their briefs until the operator releases them.

**Reply:** the queue with each PR's owner, state, and head SHA. Each verdict and the swarm that produced it. What merged and what each owner took next. Countersigns granted and why. Open operator gates. Where the collected decision trails live.
