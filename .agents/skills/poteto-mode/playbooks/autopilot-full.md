### Autopilot-full

Resolve the driver skill through [poteto-mode's Non-negotiables](../SKILL.md#non-negotiables).

**You own the verdicts, never the PRs. One owner carries each PR from build to merge-ready, and nothing merges until your swarm, which never wrote the code, has proven the code that lands and the authorized landing owner has applied the Shipping gates.**

A verdict covers one patch and green CI covers one head. Step 4 starts a full independent round at the code-ready head and at every later patch-changing push. Preserve earlier receipts only when the patch-id and dependency-applicability checks prove that they still apply. The patch-id rule in `playbooks/shipping.md` can carry a lane's result, and every new head needs its own green CI.

1. **The operator's gates come first.** The grant covers only the queue's items, so items the operator names as theirs and PRs outside the queue stop at merge-ready. A request to state the plan is not a go. On the operator's go, write the full program objective into the standing orders and restate it in your todolist, so it stands across turns until the queue is done. Before the first owner starts, tell the operator the size of the program: the number of owners, the verifier lanes in the first round, and the ceiling of two fix-forwards per PR from step 4. A program of more than three owners waits for the operator's go on that size, unless the operator's request already named it.
2. **Spawn one owner per PR, and keep its work where a replacement can find it.** Resolve the forge once for the program. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr` for every PR operation. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). Each owner is a background subagent in its own worktree that builds, opens its PR per `playbooks/opening-a-pr.md`, proves the change on the real artifact, babysits to green per `playbooks/babysit.md`, and hands the PR off at merge-ready once steps 4 and 5 clear it. No owner runs the merge.

   Open the PR early so CI and bots run alongside the work. The code is ready only after the slop-strip (the **deslop** skill, `/deslop`) and the `/no-comments` pass, so the full swarm runs on finished code. Then rebase onto current trunk and report the code-ready head before self-proof, so verification runs on the base the patch lands on. Report every later head, and merge-ready once self-proof, CI, and babysit are done. Fix rounds stay on that base unless trunk conflicts or breaks CI, because each rebase restarts CI. Run the repo's checks for the touched paths on the committed head before the code-ready push and before a later push that needs a verifier.

   Assume the owner's session dies. Soon after starting, push and start a decision trail in the program's store under `<agent-store>/orchestrate/<slug>/` per the **show-me-your-work** skill, then push after every unit worth keeping. Whoever spawns a subagent records its id, state, and a stuck-after runtime from past runs of its kind in that store, so the root can probe it if the parent dies. Force-push only your own branch, with `--force-with-lease` pinned to the SHA you last pushed or took over, and on any push you did not make, stop and report to the root.
3. **Run owners in parallel off trunk, never stacked,** so each PR lands on its own.
4. **Verify every patch-changing head.** Run the full required independent round at the code-ready head and after each patch-changing push. Carry a prior lane forward only when Shipping's patch-id and destination-applicability rule proves it remains valid. Fan out independent verifiers at the code-ready SHA per the **swarm** skill. They re-run the gates, prove the load-bearing behavior live on the real surface through the driver skill, and audit the diff. The verdict is not clean without the live lane, or before you audit the merge-ready report's receipts, because no lane trusts a claim it has not checked.

   Send every proven finding, whatever a lane labeled it, to the owner in one fix-forward, with a red test across every site with the same defect. A defect trunk shows without the PR is recorded against trunk and does not gate the PR, but one the PR copies or newly reaches is the PR's own. Never push a fix yourself, because each branch has one writer. Replace a stuck owner instead.

   Brief every review lane to report what the diff breaks, not everything wrong in the files it touches, and ask for no mutation or fuzz campaign unless the operator asked for one. Two fix-forwards per PR is the ceiling. When a blocking finding survives the second, stop work on that PR, report it blocked with the finding and its evidence, and let the operator choose another round, a narrower PR, or closing it.
5. **Land only what was independently verified on the destination it lands on.** Green CI never grants landing authority. Use the user's explicit authorization: an authorized automatic landing follows Shipping; otherwise stop at merge-ready for the operator. Once the swarm's lanes have started, merge prep rebases onto current trunk, reports the new head, and waits for green CI.

   Right before the hand-off, fetch trunk and ask whether its changes can affect the patch, because rebasing for every trunk move never ends. Rebase and wait for CI when the code that would land was never tested, as with a conflict, a file both sides changed, or a change to which checks run for the PR. A lockfile both sides changed needs no rebase when a frozen install passes on the merge result and the packages the PR changes resolve there as on the head, because that install tests the lockfile that would land, and a failing install means the rebase must repair it. When trunk changed a caller of the patch or something the patch depends on, such as code it calls or a dependency version, run the patch's checks on the merge result and hand off on a pass. Otherwise hand off. If trunk would force a third rebase past merge prep, hold and report to the root, which sequences the colliding work.

   The owner presents the merge-ready PR with its verdict and pinned head SHA to the authorized landing owner, then returns, and a fresh owner takes the next item per poteto-mode's Subagents section. If trunk moves again before the authorized landing, the patch-id rule in `playbooks/shipping.md` governs re-verification.
6. **Run the root layer.** Anything that loosens a gate, such as a raised budget or an allowlist entry, needs a verifier's proof and then your fresh countersign, because the owner is the one who wants green. Under a grant that covers approvals, that countersign is the approval, and the owner's record of it points at your countersign for a lane to check. A disabled or soft-failed check always comes out, because it stops guarding every case. Never give or bypass an approval the forge enforces, because no countersign covers it.

   On the operator's go, arm an hourly audit through the host's persistent scheduler when available and keep it until no delegated work is left. Without one, perform a bounded audit and publish a checkpoint. Each tick re-reads this playbook and the standing objective, repairs missing head or agent records through their owner, and checks every task and descendant against actual artifacts and its recorded stuck-after time. A task waiting for an answer is not stuck. Before replacing a writer, stop it and its descendants and confirm they stopped. A tick that changed something ends with a concise **ketchup** update; a tick with no changes stays quiet.
7. **Stand down at once on the operator's stop.** A hold reaches every owner as a zero-writes order. Each reports where it stands and keeps its brief until the operator releases it.

**Reply:** catch the operator up per the **ketchup** skill, covering each PR's state and verdict, what is merge-ready under the user's landing policy, countersigns and why, and open operator gates, with links to each PR and the trails.
