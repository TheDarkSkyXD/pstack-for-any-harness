### Autopilot-stack

**You own the stack, never the landing. Build and verify the queue with full autonomy, then hand the operator one linear Graphite stack to review and land.** The sibling of **Autopilot-full**.

1. **Run the owner loop unchanged.** One remote or isolated agent per PR owns its change end to end: build, registration in the repository's stacking workflow, self-proof (gates, CI, receipts), skeptical automated-review triage per `../references/bugbot-triage.md`, the available code-cleanup pass, `.agents/skills/no-comments/SKILL.md`, and babysit to green per `playbooks/babysit.md`. Owners parallelize when the work is self-contained. Every owner starts a `decisions.tsv` trail, pushes its first branch snapshot, and opens a ready PR within about 15 minutes. As subagents start, the owner records each ID, expected runtime, and state in an uncommitted `children.tsv`. The owner reports the final code-ready SHA and every later patch-changing SHA. Run self-proof, CI, babysit, and root verification in parallel. Before each round-starting push, run the repo's pre-review checks on the committed head. Every owner returns its decision trail and child list in its report.
2. **Audit on the wake chain.** The root runs an audit tick roughly every 30 minutes. Schedule it through the active harness's recurring terminal, monitoring, or wake mechanism; never leave cadence to memory or lossy completion notifications. At each tick, re-read this playbook from trunk and the active goal, audit against both, and fix drift. Probe each owner and collect decision trails. Count only side effects as progress. A lane that errors or passes its expected runtime without a side effect is stuck; stop it and dispatch a replacement. Check the platform agent list and every owner's `children.tsv`; record and replace stuck child work too. A stall never proves or drops the work. Post a concise status update only for a tracked change no earlier update reported: PR opened, code-ready head, verification round started or closed, verdict, merge, stuck owner and response, blocker opened or cleared, or operator decision. Name only new changes; do not repeat a queue table or unchanged blockers. If nothing changed, end without reply text. Log each tick in the root's decision trail, listing reported changes or `none`.
3. **Hold the operator gates.** State-then-wait, so a request to state the plan is not a go. On the operator's explicit go, arm the active harness's persistent goal mechanism with the full program objective. Keep the goal active across turns until the chain is done. On the operator's stop, every owner takes an immediate zero-writes hold.
4. **Verify every round, then STACK-READY.** A round starts at the code-ready SHA and every later push that changes the PR patch. Fan out independent verifiers per the **swarm** skill: rerun gates at that SHA, prove load-bearing behavior live on the real surface, and use two or more focused audit lanes over the receipts and diff. Run a regression lane on trunk; if trunk lacks the feature, record that and verify the added behavior and expected end state. Treat defects filed as notes as findings. Send all proven findings to the owner in one fix-forward; request a red test for behavior defects or a repro receipt when no test can expose them. The next round brief must include the defect. Preserve lane results only when the patch-id rule in `playbooks/shipping.md` says they remain valid. The owner reports STACK-READY with the exact head SHA after self-proof, CI, and babysit finish. Nothing enters the stack without a clean verdict for a matching patch.
5. **Append on a clean verdict, never ship.** No owner merges, arms auto-merge, or closes. A clean verdict appends the PR to the one linear Graphite stack, in verified order or an order the operator specified.
6. **Single writer on topology, parallel writers on builds.** Stack mechanics follow Graphite (`gt`), with the division of labor the cloud environment forces. An owner pushes only its own branch, `git push --force-with-lease` after an ls-remote check, and reports its tip and intended parent. The root owns stack topology and registers each append locally: `gt track -p <current-tip>`, then `gt submit --no-interactive --stack` from the tip. `gt submit` walks from trunk, and a cloud agent must never pull branches below its own into that walk; when instructed, it may set its bottom PR's base directly instead.
7. **Absorb drift at the root, then re-verify what moved.** The root absorbs trunk movement by restacking the chain (`gt restack`, `gt sync`); when a restack surfaces conflicts in an owner's files, that owner fixes its own slice and the root pushes the result. A restack rewrites every SHA above it and voids verdicts at old SHAs. Compare `git patch-id` at each verdict SHA against the new head and apply the noise procedure in `playbooks/shipping.md`. Anything else that drifted goes back through step 4 before delivery. The countersign rule is unchanged from Autopilot-full. A genuinely new pin raises a stop for the root's fresh countersign. Absorbing drift of landed values is not a raise.
8. **Deliver the chain.** The deliverable is one linear chain of verified PRs, reviewable bottom-up in the Graphite UI, every link carrying its verifier verdict in the PR body or a comment. The operator reviews and lands it, with their own clicks or by arming merge-when-ready.

**Choosing between the autopilots.** Autopilot-full when the PRs are independent and landing authority is granted. Autopilot-stack when the operator wants review before landing, the work is sequenced or coupled, or merge authority is withheld.

**Reply:** links to the stack root and tip, a one-line verdict summary per link, and anything parked or excluded with the reason.
